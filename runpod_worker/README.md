# Воркер генерации фото персонажа для RunPod

Отдельный сервис: SDXL + IP-Adapter FaceID на арендованной карте, с HTTP API. Никаких внешних
провайдеров генерации — всё считается на поде.

Структура повторяет `C:\projects\WET\WetDreams\runpod\wai-nsfw-illustrious-sdxl`: конфигурация,
схемы данных, генерация, хранилище задач, метрики и точка входа разнесены по отдельным модулям,
маршруты API называются так же.

## Чем отличается от WetDreams

| | WetDreams | здесь |
|---|---|---|
| Идентичность | нет — каждый кадр сам по себе | IP-Adapter FaceID, эмбеддинг персонажа хранится |
| Метрика лица | нет | cosine ArcFace в каждом ответе, порог отбраковки |
| LoRA | объявлена в схеме, `_apply_lora_weights` пишет «not yet implemented» | реализована |
| Очередь | RabbitMQ, несколько подов | задачи в памяти, один под |
| Хранилище | S3 | файлы на сетевом томе |

Очередь на RabbitMQ здесь сознательно не повторена: она нужна, когда подов несколько и нагрузка
идёт от пользователей. Для пакетной генерации паков на одном поде это лишний узел. Интерфейс
`job_store.py` совпадает по смыслу, поэтому замена на Redis/RabbitMQ не затронет остальной код.

## Что уже измерено

Фактический прогон этого пайплайна, RTX 4090 Secure Cloud, $0.74/час
(`deliverables/BENCHMARK.md`):

| | значение |
|---|---|
| Чекпойнт | RealVisXL V5.0, fp16 |
| Идентичность | IP-Adapter FaceID `ip-adapter-faceid_sdxl.bin`, scale 0.95 |
| Схема кадра | 1024×1024, 28 шагов, DPM++ 2M Karras → hires ×1.5 → **1536×1536** |
| Время кадра | **8.91 с** |
| Стоимость кадра | **$0.00183** |
| Лицо к эталону | **0.727** в среднем (0.676–0.753) |

Шкала откалибрована: портреты заведомо чужих людей на этой же модели дают до **0.387**
(`scripts/calibrate_similarity.py`), поэтому порог 0.5 — измеренная граница, а не назначенная.

## Запуск

```bash
docker build -f runpod_worker/Dockerfile -t character-worker .

docker run --gpus all -p 8000:8000 \
  -v /path/to/models:/models \
  -v /path/to/data:/data \
  -e WORKER_API_KEY=секрет \
  -e HF_TOKEN=... \
  character-worker
```

На RunPod: том монтируется в `/models` (веса) и `/data` (персонажи и результаты). Оба каталога
обязаны пережить пересоздание пода — эмбеддинг персонажа невосстановим.

Локально, без Docker:

```bash
python -m runpod_worker.worker --mode both
```

`--mode warmup` прогревает веса и выходит. Это не удобство, а деньги: первый запрос иначе тянет
SDXL, IP-Adapter и InsightFace внутри себя, и минуты загрузки тарифицируются как GPU-время.

## API

| Маршрут | Назначение |
|---|---|
| `GET /health` | карта, VRAM, загруженные модели, число персонажей |
| `GET /metrics` | Prometheus: сгенерировано, принято, отбраковано, среднее время и метрика |
| `GET /models` | доступные чекпойнты |
| `POST /characters` | создать персонажа из эталона или сгенерировать эталон по описанию |
| `GET /characters` | список |
| `POST /generate/sync` | один кадр, ответ по готовности |
| `POST /generate` | один кадр задачей |
| `POST /generate/batch` | **пак кадров одного персонажа** — основной сценарий |
| `GET /job/{id}` | статус и результаты |

Все маршруты генерации требуют заголовок `X-Api-Key`, если задан `WORKER_API_KEY`.

### Создать персонажа

```bash
curl -X POST localhost:8000/characters -H "X-Api-Key: секрет" \
  -H "Content-Type: application/json" -d '{
    "name": "nova",
    "prompt": "studio portrait of a 30 year old woman, dark brown wavy hair, hazel eyes"
  }'
```

Эталон можно и передать готовым — `reference_image` (base64) или `reference_path`.

### Пак из восьми сцен

```bash
curl -X POST localhost:8000/generate/batch -H "X-Api-Key: секрет" \
  -H "Content-Type: application/json" -d '{
    "character": "nova",
    "base_seed": 20260905,
    "scenes": ["candid photo in a sunlit kitchen", "walking down a city street at golden hour"]
  }'
```

Сид кадра — `base_seed + 1000·i`. Шаг в тысячу, а не единица: соседние кадры иначе делят близкий
шум и выходят похожими композициями. Весь пак воспроизводится одним числом.

Ответ каждого кадра содержит `similarity`, `accepted` и `reject_reason` — кадр без замера ничего
не подтверждает, поэтому метрика в контракте, а не в логе.

## LoRA

Реализована по-настоящему: `service._apply_lora` грузит веса, снимает предыдущий адаптер (иначе
diffusers складывает их друг на друга) и задаёт силу. Файлы кладутся в `LORA_DIR`, в запросе
указывается `lora` и `lora_scale`.

**Про `nova_character_lora.safetensors` из `Synthetic_Character_WIP/07_flux_lora_v2`.** Файл есть
(89.7 МБ, 684 тензора), но использовать его здесь нельзя и полагаться на него не стоит:

1. Это адаптер под **FLUX** (`transformer.single_transformer_blocks.*`), а тут SDXL. Ключи
   тензоров не совпадают, diffusers его отвергнет.
2. Обучение той ветки закончилось метрикой **0.54**, и контрольный прогон с триггером и без
   показал, что адаптер к триггеру не привязался.
3. Ненулевые нормы `lora_B` доказательством обучения не являются: при
   `init_lora_weights="gaussian"` они ненулевые с самого начала.

То есть рабочая идентичность здесь держится на IP-Adapter FaceID (0.727), а не на LoRA. Если
LoRA понадобится — её нужно обучать заново под SDXL и проверять контролем с триггером и без.
