# Synthetic Character Pipeline — план

Продолжение линейки WetDreams (`C:\projects\WET`): у продукта уже есть боевой RunPod-воркер на
Illustrious/Pony-SDXL чекпойнтах, который на каждый запрос рисует персонажа заново по промпту —
устойчивого лица между генерациями нет. Этот проект добавляет именно это: одно и то же
узнаваемое лицо на 8 фото + видео. LoRA-хуки в проде WetDreams заведены в схеме
(`lora_weights` в `GenerationRequest`), но не реализованы — значит IP-Adapter FaceID здесь не
временный обходной путь, а на сегодня единственный рабочий вариант identity-lock вообще.

Реализовано в [worker/](worker/) как `ModelManager` + `Generator` — тот же архитектурный паттерн,
что `generation.py` у WetDreams (загрузить модель → собрать kwargs → засечь время → вызвать
pipeline → обработать результат), чтобы код было можно напрямую перенести в их прод-воркер.
Главное отличие: у них `nsfw_score` в результате объявлен, но остаётся `None` ("could implement
here" в комментарии) — здесь этот же слот реально считается через `safety/moderation_pipeline.py`
и дополнен возрастом и похожестью на watchlist, которых у них нет вообще. Подробности — см.
[deliverables/PIPELINE.md](deliverables/PIPELINE.md).

## 1. Архитектура пайплайна

```
[Character Bible]                 текстовое описание внешности, без референса реального человека
       │
       ▼
[Stage 0: Reference face]         txt2img, SDXL/фотореал-чекпойнт, фиксированный seed → 1 эталонное лицо
       │
       ▼
[Stage 1: Identity lock]          InsightFace (antelopev2) извлекает face embedding из эталона
       │
       ▼
[Stage 2: 8 фото]                 SDXL + IP-Adapter FaceID(-Plus) с этим embedding,
                                   8 разных промптов (сцена/поза/одежда/свет), seed = base_seed + i
       │
       ▼
[Stage 3: Safety gate (фото)]     NSFW-классификатор + возрастной эстиматор + face-similarity
                                   против watchlist. Не прошло — не идёт дальше.
       │
       ▼
[Stage 4: Image-to-video]         1 фото из восьми → LTX-Video / Wan2.1 I2V, 5 сек
       │
       ▼
[Stage 5: Safety gate (видео)]    покадровая проверка (каждый N-й фрейм) теми же классификаторами
       │
       ▼
[Stage 6: Benchmark log]          время, стоимость, параметры → таблица
```

Ключевое архитектурное решение: **identity через IP-Adapter FaceID, не через LoRA-обучение**.
LoRA на лицо требует датасета 15-30 фото этого же лица под разными углами — а взять их неоткуда,
раз лицо синтетическое и должно сгенерироваться первым. Стандартный обходной путь (studio-практика):
сгенерировать 8 фото через FaceID, и только если нужна ещё более высокая точность для будущих
генераций — дообучить LoRA на этих же 8+ фото как на собственном датасете. Для объёма этого задания
(8 фото + 1 видео) IP-Adapter FaceID(-Plus v2) для SDXL достаточен и в разы дешевле по GPU-часам,
чем LoRA-тренировка (которая сама по себе стоит времени и денег на отдельном шаге).

## 2. Модели

| Роль | Модель | Почему |
|---|---|---|
| Base checkpoint | SDXL 1.0 base + фотореал-финетюн (выбор чекпойнта — за тобой, см. REQUIREMENTS) | стандарт для controllable photoreal генерации, совместим с IP-Adapter FaceID |
| Identity conditioning | IP-Adapter-FaceID-PlusV2 (h94/IP-Adapter-FaceID, SDXL веса) | лучшее качество identity-lock из открытых решений на конец 2025 |
| Face embedding | InsightFace `antelopev2` (buffalo_l как fallback) | тот же эмбеддинг идёт в IP-Adapter и в safety-проверку (age/similarity) — не нужна вторая модель |
| Видео (I2V) | LTX-Video 0.9.5 (основной вариант) | самый быстрый и лёгкий по VRAM self-hosted I2V на конец 2025, укладывается в бюджет по GPU-часам; Wan2.1-14B — запасной вариант при более высоких требованиях к качеству движения, но дороже и медленнее |
| NSFW-классификатор | Falconsai/nsfw_image_detection (ViT, self-hosted через transformers) | не требует внешнего API, работает офлайн на том же поде |
| Возрастной эстиматор | атрибут age из InsightFace buffalo_l + доп. проверка vit-age-classifier | эвристика, не юридическое доказательство возраста — см. раздел Safety |

## 3. Seed-логика

- `base_seed` фиксируется один раз на персонажа (например, дата запуска в виде числа) — это то,
  что делает лицо воспроизводимым между сессиями.
- Эталонное лицо (Stage 0): `seed = base_seed`.
- Каждое из 8 фото: `seed = base_seed + 1000*i` (i = 1..8) — разброс seed достаточно большой, чтобы
  не повторять композицию, но identity держится не сеpartом, а FaceID-эмбеддингом, так что сцена/поза
  меняется свободно без потери лица.
- Видео: тот же `base_seed`, что у исходного фото + отдельный `motion_seed` для видео-модели (LTX/Wan
  сэмплируют шум движения отдельно от шума кадра).
- Все seed логируются в benchmark-таблицу — это обязательное поле, иначе воспроизвести конкретный
  кадр повторно нельзя.

Логика реализована в [worker/seed_manager.py](worker/seed_manager.py).

## 3.1. Промпты для 8 сцен

Вместо ручного написания 8 промптов — [pipeline/prompt_engineering.py](pipeline/prompt_engineering.py)
разворачивает короткий сцена-бриф ("office, business suit, morning light") в полный теговый
SDXL-промпт через LLM (OpenRouter, тот же провайдер, что уже используется в WetDreams). Паттерн
взят из продового `image_prompt_templates/realistic.txt` WetDreams, адаптирован под статичный
список сцен вместо чата: там LLM каждый раз брала "текущую" сцену из последних сообщений диалога,
здесь сцены заданы заранее в character bible, LLM только разворачивает каждую в промпт, сохраняя
неизменные черты персонажа во всех восьми. Safety-формулировка внутри промпта переключается одним
параметром `ContentProfile` (SFW / WETDREAMS_NSFW) — см. REQUIREMENTS_FROM_USER.md, п.3.

## 4. Хостинг / деплой

- Провайдер по умолчанию: **RunPod** (Community Cloud, оплата за секунду, шаблон ComfyUI или
  чистый PyTorch-под с SSH). Vast.ai — как более дешёвая альтернатива при готовности к менее
  стабильному аптайму.
- GPU по умолчанию: **RTX 4090 24GB** — хватает для SDXL+IPAdapter (пик ~14-16GB VRAM) и для
  LTX-Video 5 сек 768p (~18-20GB VRAM). Для Wan2.1-14B нужен A6000/A100 48GB+.
- Под поднимается по требованию на время генерации и останавливается сразу после — это определяет
  всю модель стоимости (см. deploy/cost_calculator.py).
- Установка: Docker-образ `runpod/pytorch` + `diffusers`, `insightface`, `transformers`,
  веса моделей качаются при первом старте пода на network volume, чтобы не платить за скачивание
  повторно на каждом перезапуске.

Пошагово — [deploy/runpod_setup.md](deploy/runpod_setup.md).

## 5. Safety-слой

Три независимых проверки, все self-hosted (без внешних платных API):

1. **Промпт-фильтр (до генерации).** Regex/keyword deny-list на возрастные и identity-риски
   термины ("child", "school uniform" вне взрослого контекста, имена реальных людей/селебрити)
   + опциональный ML-классификатор текста. Блокирует генерацию до того, как она началась.
2. **NSFW/контентная проверка (после генерации).** ViT-классификатор на каждое фото и на
   каждый N-й кадр видео.
3. **Возраст + реальное лицо (после генерации).**
   - Возраст: атрибут age из face-embedding модели, порог с запасом (отклонять всё, что модель
     оценивает моложе ~25, при целевом персонаже "выглядит на 28-35") + ручной визуальный ревью
     перед публикацией — возрастная эстимация по фото это эвристика, не доказательство, поэтому
     финальный гейт всегда человек.
   - Реальное лицо: cosine similarity ArcFace-эмбеддинга сгенерированного лица против
     watchlist-галереи эмбеддингов (публичные фигуры + любой список "не быть похожим на X" от
     заказчика). Полной проверки "не похож ни на одного человека на Земле" self-hosted
     инструментами не существует — это ограничение всей индустрии, не только этого пайплайна.
     Снижение риска на входе: эталонное лицо генерируется из текстового промпта в чистом
     латентном шуме, а не морфингом/img2img с реального фото — то есть коллизия может быть только
     случайной, не унаследованной.

Код — [safety/moderation_pipeline.py](safety/moderation_pipeline.py).

## 6. Бенчмаркинг

Каждый вызов `PhotoGenerator.generate()` / `VideoGenerator.generate()` автоматически пишет строку
в [benchmarking/benchmark_log.csv](benchmarking/benchmark_log.csv) через
[worker/benchmark.py](worker/benchmark.py): модель/чекпойнт, IP-Adapter параметры, seed,
разрешение, шаги, время генерации (сек), $/час GPU, стоимость этой генерации, результат
safety-гейта. Стоимость считается [deploy/cost_calculator.py](deploy/cost_calculator.py) из двух
чисел: измеренное время + тариф GPU-провайдера — руками таблица не заполняется, только тариф
GPU передаётся в CLI флагом `--hourly-rate`.

Критерий "фото < 40 сек": на RTX 4090, SDXL 1024×1024, 28-30 шагов, DPM++ 2M Karras,
с уже прогретой моделью в VRAM (без учёта холодного старта пода) — реалистично 8-15 сек/фото,
запас по бюджету времени есть. Холодный старт пода (первая загрузка весов) в этот показатель
не считается — это отдельная фиксированная стоимость на сессию, а не на фото.

## 7. Порядок работ

1. Утвердить character bible (внешность, "легенда" персонажа) — шаблон в
   [character/character_bible_template.md](character/character_bible_template.md).
2. Поднять под на RunPod, установить окружение (deploy/runpod_setup.md).
3. `python pipeline/generate_photos.py --output-dir ... --base-seed ... --hourly-rate ...` —
   эталонное лицо + 8 фото, safety-гейт и запись в benchmark_log.csv происходят автоматически
   внутри `worker/photo_generation.py`.
4. `python pipeline/image_to_video.py --input-photo ... --photo-index N --hourly-rate ...` —
   video, safety-гейт по кадрам и запись в benchmark_log.csv автоматически внутри
   `worker/video_generation.py`.
5. Скопировать заполнившиеся числа из `benchmarking/benchmark_log.csv` в
   `deliverables/BENCHMARK.md` (готовый шаблон таблицы для отправки).
6. Собрать итоговую выдачу: 8 фото + видео + `deliverables/PIPELINE.md` +
   `deliverables/BENCHMARK.md` + `deliverables/SAFETY.md`.

Шаги 2-5 требуют реально арендованного GPU — см. [REQUIREMENTS_FROM_USER.md](REQUIREMENTS_FROM_USER.md).
Код и архитектура (шаги 1, 6) готовы уже сейчас — см. [worker/](worker/), протестировано локально
(без официальных цифр — см. README.md, раздел "Статус").
