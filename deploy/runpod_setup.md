# Деплой на RunPod

Обновлено по факту реального прогона (не только теория) — см. отметки "проверено на поде".

## 1. Под

- **Secure Cloud, не Community Cloud.** Проверено на поде: у Community Cloud хостов SSH работает
  только через ограниченный прокси `ssh.runpod.io`, который требует юзернейм вида
  `[POD_ID]-[HASH]`, а этот хеш доступен только через веб-интерфейс ("Connect" в дашборде) — по API
  его получить не удалось. Кроме того, у конкретного Community-хоста, на котором тестировалось,
  вообще не публиковался прямой TCP-порт даже после `--ports 22/tcp` при создании и после апдейта.
  Secure Cloud сразу даёт публичный IP + порт для полноценного SSH/SCP. Цена выше
  (RTX 4090: Community ~$0.34/час, Secure ~$0.74/час на момент проверки — актуальные цифры смотреть
  `GET https://api.runpod.io/v2/catalog/gpus`), но при разовой сессии (меньше часа) разница в
  центах, а не в долларах.
- GPU: RTX 4090 24GB (дефолт) или A6000/A100 48GB+ (если для видео выбран Wan2.1-14B вместо
  LTX-Video).
- Template: `runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04`.
- `--containerDiskSize 45` с запасом (SDXL ~7GB, IP-Adapter FaceID ~1.7GB, LTX-Video веса,
  InsightFace ~300MB, сам HF/pip кеш).
- `--startSSH --ports "22/tcp"` **обязательно указать при создании пода**, не добавлять потом
  через `pod update` — на Secure Cloud первый способ отработал, апдейт после факта создания
  (пробовалось на Community) не публиковал порт вообще.

## 2. Инструмент — `runpodctl`, не голый REST/GraphQL

```bash
curl -sL "https://github.com/runpod/runpodctl/releases/latest/download/runpodctl-windows-amd64.exe" -o runpodctl.exe
./runpodctl.exe config --apiKey "$RUNPOD_API_KEY"   # сам генерирует ed25519-ключ и
                                                      # регистрирует его в аккаунте — не нужно
                                                      # делать это руками через веб-интерфейс
./runpodctl.exe create pod \
  --name "<name>" --secureCloud \
  --gpuType "NVIDIA GeForce RTX 4090" --gpuCount 1 \
  --imageName "runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04" \
  --containerDiskSize 45 --volumeSize 5 --cost 1.0 \
  --startSSH --ports "22/tcp" --mem 24 --vcpu 4

./runpodctl.exe ssh info <podId>   # ждать, пока не появится "ssh_command" с реальным ip/port
                                     # (на Secure Cloud — обычно первая же попытка сразу после
                                     # RUNNING; поле "host" в JSON появляется не всегда, ориентир —
                                     # наличие "ssh_command")
```

SCP работает нормально на прямом SSH (не через `ssh.runpod.io` прокси, у которого SCP/SFTP
отключены намеренно). Код на под — обычным `scp`/`tar` через SSH, не через `runpodctl send`.

## 3. Установка окружения — ставить ML-стек ОДНОЙ командой, не по пакету

**Проверено на поде — реальная проблема, не гипотетическая:** база `runpod/pytorch:2.4.0-...`
идёт с `torch==2.4.1+cu124`. Если ставить `diffusers`/`transformers`/`insightface` отдельными
`pip install` командами по одной, pip не согласовывает версии между вызовами, и получается
рассинхрон: последняя версия `transformers` требует `torch>=2.5`, "просто" `pip install -U torch`
без указания индекса ставит билд под CUDA 13 (а драйвер на поде поддерживает только CUDA 12.4) —
итог: CUDA полностью отваливается ("NVIDIA driver on your system is too old"). Правильный порядок:

```bash
# 1. torch — конкретную версию, из cu124-индекса, а не "-U" в пустоту:
pip install torch==2.6.0 torchvision==0.21.0 torchaudio==2.6.0 \
    --index-url https://download.pytorch.org/whl/cu124
# (проверить, какие версии реально есть на индексе: pip index versions torch --index-url ...)

# 2. весь HF-стек ОДНОЙ командой, чтобы резолвер pip согласовал версии между собой:
pip install --upgrade transformers diffusers accelerate huggingface-hub tokenizers safetensors

# 3. остальное:
pip install insightface onnxruntime-gpu pydantic imageio imageio-ffmpeg requests
```

**onnxruntime-gpu vs onnxruntime — не ставить оба.** Они делят один и тот же модуль
`onnxruntime`, и если оба установлены (или один поставлен поверх другого), InsightFace откатывается
на `CPUExecutionProvider` молча, без явной ошибки — только предупреждение в логе. Проверить:
`python -c "from insightface.app import FaceAnalysis; a=FaceAnalysis(name='buffalo_l'); a.prepare(ctx_id=0)"`
и посмотреть на строку `Applied providers: [...]` — должно быть `CUDAExecutionProvider`, не только
`CPUExecutionProvider`. **Ещё один реальный нюанс:** сама `onnxruntime-gpu` последней версии на
PyPI тоже может быть собрана под CUDA 13 (`libcublasLt.so.13: cannot open shared object file`) —
на тот же случай несовпадения с драйвером 12.4. Если это произошло — CPU-провайдер не блокирует
работу (детект лица на CPU занимает доли секунды на кадр против ~15 сек SDXL-шага), можно просто
жить с этим для разового прогона, не тратить время на подбор точной версии onnxruntime-gpu под
CUDA 12.

**InsightFace: `buffalo_l`, не `antelopev2`.** Проверено на поде: `FaceAnalysis(name='antelopev2')`
падает с `AssertionError: assert 'detection' in self.models` — известная проблема с хостингом
именно этого конкретного пака (архив скачивается не полностью/не с того зеркала). `buffalo_l`
скачивается и работает надёжно (все 5 суб-моделей: detection, recognition, genderage,
landmark_2d_106, landmark_3d_68).

## 4. HuggingFace и Civitai токены — что на самом деле нужно

- **IP-Adapter-FaceID (h94/IP-Adapter-FaceID) — НЕ gated.** Проверено прямым запросом с реальным
  токеном: скачивается без каких-либо предварительных "agree to access" на сайте. Несёт
  некоммерческую лицензию (унаследована от InsightFace) — это лицензионное ограничение, не
  технический барьер загрузки.
- **HuggingFace токен не требует пополнения баланса** ни для одной операции здесь — скачивание
  весов (gated или нет) всегда бесплатно, баланс на аккаунте относится только к платным сервисам
  (Inference Endpoints, Spaces GPU и т.п.), которые в этом пайплайне не используются.
- **LTX-Video (Lightricks/LTX-Video) числится gated на странице репозитория**, но конкретный
  проверенный токен реально скачал `model_index.json` (HTTP 200 через редирект) без отдельного
  подтверждения лицензии — доступ, видимо, уже был на аккаунте. Если у другого токена/аккаунта
  доступа нет — нужно зайти на https://huggingface.co/Lightricks/LTX-Video под своим аккаунтом и
  принять лицензию, это ручной шаг через браузер, API-обхода нет.
- CIVITAI_TOKEN нужен только если выбран один из трёх Illustrious/Pony-чекпойнтов вместо дефолтного
  ванильного SDXL (см. REQUIREMENTS_FROM_USER.md, п.2).

## 6. Замер времени и стоимости — автоматический

`worker/benchmark.py` сам дописывает строку в `benchmarking/benchmark_log.csv` после каждого
`generate()` — не нужно вручную вызывать `deploy/cost_calculator.py` после каждого фото, только

## 7. Остановка/удаление пода

`./runpodctl.exe remove pod <podId>` сразу после того, как результаты скачаны с пода (`scp` или
`tar czf - path | ssh ... > local.tar.gz`, т.к. `ssh.runpod.io`-прокси SCP не поддерживает, а
прямой SSH на Secure Cloud — поддерживает). GPU-время после последней генерации тарифицируется
зря, если под не остановлен.

## 8. Uncensored-чекпойнты, identity и скорость

Заказчик прислал несколько ссылок. Главное, что выяснилось при проверке: **все они — LoRA или
адаптеры, а не самостоятельные модели**, и их базы определяют, что с чем сочетается.

### 8.1. Фото: сильные модели без ограничений

Две оси, которые постоянно смешивают, а они независимы:

1. **Контентные ограничения** — есть ли цензура в весах.
2. **Лицензия** — разрешено ли коммерческое использование.

Модель бывает свободной по одной оси и связанной по другой. `FLUX.1-dev` + `Flux-uncensored`
свободен по первой и запрещён по второй (BFL Non-Commercial). Ниже оси разведены явно.

| `--photo-model` | Репозиторий | Архитектура | FaceID | Лицензия |
|---|---|---|---|---|
| `chroma` | `lodestones/Chroma1-HD` | DiT (Flux 8.9B) | **нет** | **apache-2.0** |
| `lustify` | `John6666/lustify-sdxl-nsfwsfw-v2-sdxl` | SDXL | да | creativeml-openrail-m |
| `pony-realism-uncensored` | `nesaorg/PonyRealism-Uncensored` | SDXL | да | **не заявлена** |
| `pony-realism` | `John6666/pony-realism-v23-sdxl` | SDXL | да | other |
| `noobai-xl` | `Laxhar/noobai-XL-1.1` | SDXL (аниме) | да | other |
| `illustrious-uncensored` | `John6666/illustrious-xl10-...-v30-sdxl` | SDXL (аниме) | да | other |

**Chroma1-HD — единственный вариант, свободный по обеим осям.** 8.9B на архитектуре
FLUX.1-schnell, переобученный без фильтра, apache-2.0 вместо некоммерческой лицензии
FLUX.1-dev. В отличие от schnell дистилляция снята: работает настоящий CFG и `negative_prompt`.
В diffusers поддержан **нативно** — `ChromaPipeline` есть в 0.35.2 (проверено импортом), это не
community-файл, который развалится на следующей версии, как случилось с InstantID.

Плата за это — архитектура DiT, а не SDXL UNet, поэтому **IP-Adapter FaceID к нему не
подключается**, как и к любому Flux. В конфиге стоит `supports_faceid: False`, и попытка
запросить identity даёт явную ошибку. Это сделано намеренно: `load_ip_adapter` на таком пайплайне
может отработать без исключения, а identity просто не долетит до модели — заметно только по
случайным лицам на готовых кадрах. Именно так уже было потеряно GPU-время на InstantID.

**LUSTIFY v2.0 — лучший выбор, если личность нужна.** Самый используемый реалистичный NSFW-SDXL
(десятки тысяч скачиваний против сотни у переупаковки PonyRealism), лицензия
creativeml-openrail-m — та же, что у ванильного SDXL, коммерческое использование разрешено. Это
единственная строка таблицы, где сходятся все три: нет цензуры, работает FaceID, внятная лицензия.

**Про `nesaorg/PonyRealism-Uncensored`:** лицензия не заявлена вообще. Отсутствие заявления — не
разрешение; для коммерческого сценария это хуже, чем ограничительная лицензия. Оставлен в
конфиге, но дефолтом брать `lustify`.

Chroma требует bfloat16 (Flux-линейка на fp16 даёт NaN в attention) и ~19 GB весов плюс T5 — на
24 GB только с оффлоадом, на 48 GB свободно.

### 8.2. Три режима FaceID

`IDENTITY_MODES` в `worker/config.py`, флаг `--identity-mode`. Режимы отличаются не только файлом
весов, но и **кодом инференса** — отсюда отдельная ветка на каждый в
`worker/photo_generation.py::_build_face_embeds`.

| Режим | Веса | Что нужно сверх base | scale |
|---|---|---|---|
| `base` | `ip-adapter-faceid_sdxl.bin` | — | 0.95 |
| `portrait` (дефолт) | `ip-adapter-faceid-portrait_sdxl.bin` | N эталонов вместо одного | 0.8 |
| `plusv2` | `ip-adapter-faceid-plusv2_sdxl.bin` | CLIP-энкодер + `reference_image_path` | 0.7 |

Формы тензора `ip_adapter_image_embeds` (проверено прогоном на CPU, `uncond`-половина нулевая во
всех случаях):

- `base` / `plusv2`, один эталон → `(2, 1, 1, 512)`
- `portrait`, N эталонов → `(2, N, 512)`; при одном эталоне → `(2, 1, 512)`

Ветка выбирается **по режиму, а не по количеству переданных эмбеддингов**: портретный проектор
ждёт `(b, n, 512)` всегда, включая `n=1`. Если ветвиться по наличию `face_embeddings`, запрос с
одним эталоном молча уходил бы в base-форму с лишней осью.

**Что означает `portrait` для Stage 0.** Режиму нужно несколько ракурсов одного человека, иначе
он вырождается в `base` с лишним слоем. Поэтому Stage 0 теперь генерирует не один эталон, а
`REFERENCE_ANGLES` (5 штук: фронтальный + два три-четверти + профиль + наклон), seed со смещением
100 на ракурс. Приписки к промпту — про геометрию съёмки, не про эмоции: проектор усредняет лица,
и разные выражения он усреднит тоже, дав смазанную мимику на всех восьми кадрах.

**PlusV2 требует `reference_image_path`, а не только эмбеддинг.** Он работает на паре
ArcFace + CLIP, а CLIP считается по изображению. CLIP-энкодер (`laion/CLIP-ViT-H-14`) должен быть
частью пайплайна ещё **до** `load_ip_adapter` — досоздать его потом нельзя,
`prepare_ip_adapter_image_embeds()` ищет `pipeline.image_encoder`. Сам CLIP-эмбеддинг ставится
атрибутом в проекционный слой UNet: публичного API для этого нет, официальный пример diffusers
делает так же. `shortcut=True` — это и есть отличие v2 от v1, не настройка на вкус.

У `base` и `plusv2` в репозитории есть парные LoRA, у `portrait` своей нет — это свойство
варианта, а не упущение.

**Не проверено на GPU:** `portrait` и `plusv2` в этом проекте ещё не запускались. Формы тензоров
сверены с референсной реализацией h94 и прогнаны на CPU, но первый прогон на поде надо делать на
одном кадре, а не сразу на восьми.

### 8.3. Видео: развилка есть, и она неустранима

Формулировка «A14B = uncensored-ветка» неточна и была исправлена: **LightX2V — это в первую
очередь дистилляция скорости** (генерация за 4 шага вместо ~30), а не снятие ограничений.
Репозиторий `rzgar/...` — это готовый мердж скоростной LoRA LightX2V с контентными LoRA. Поэтому
ветки правильнее называть по тому, что они дают:

| Ветка | База | Identity | Скорость | Лицензия |
|---|---|---|---|---|
| Identity video | `Wan2.2-TI2V-5B` | `JonneyWang/AnyID` | обычная (~30 шагов) | база Apache-2.0, **AnyID CC BY-NC-SA 4.0** |
| Fast video | `Wan2.2-I2V-A14B` | нет | 4 шага | база Apache-2.0, `rzgar/...` Apache-2.0 |

Лицензии проверены через HF API, не по памяти: `Wan-AI/Wan2.2-TI2V-5B`, `Wan-AI/Wan2.2-I2V-A14B`,
`lightx2v/Wan2.2-Lightning` и `rzgar/Wan2.2_LightX2V_4Step_Uncensored` — все `apache-2.0`. То
есть **ограничивающая лицензия во всей видео-части ровно одна — у AnyID**, и она же
единственная, что мешает коммерческому использованию identity-ветки.

LoRA от одной ветки на другую не встаёт: пара `high`/`low` у LightX2V существует именно потому,
что A14B — MoE из двух экспертов. **Совместить в одной генерации нельзя.** Проверено через HF API
(`base_model:adapter:Wan-AI/Wan2.2-TI2V-5B`, 21 адаптер): скоростной 4-шаговой LoRA под TI2V-5B
среди них нет, поэтому «ускорить identity-ветку тем же приёмом» на сегодня не выйдет.

**AnyID** (`deploy/anyid_video_setup.sh`) — LoRA rank/alpha 256 к TI2V-5B, CVPR 2026, принимает до
5 фото или 1 видео как референс. Три оговорки:

- Подключается **не** через `load_lora_weights`: LoRA нужно предварительно вмерджить в DiT их
  скриптом `merge_lora.py`, инференс идёт через их `generate.py`. Это чужой пайплайн целиком, а не
  веса к нашему — отсюда отдельный скрипт, а не запись в `VIDEO_MODEL_CONFIGS`.
- Нужен **оригинальный** `Wan-AI/Wan2.2-TI2V-5B`, не `-Diffusers`: разные раскладки одних и тех же
  весов, подменить одну другой нельзя. В `worker/config.py` у нас стоит именно Diffusers-вариант.
- 50 скачиваний, июль 2026 — свежая исследовательская работа, не обкатанная в проде.

### 8.4. Лицензии и safety — сводка

**Ни у одной модели в обеих ветках нет встроенного safety-фильтра.** Это верно и для баз Wan, и
для SDXL-финетюнов, и для адаптеров FaceID: `StableDiffusionXLPipeline` в diffusers не несёт
safety_checker, у Wan-пайплайнов его нет тем более.

Практически это ничего не меняет для проекта: фильтрация здесь **своя** и не зависит от модели —
`safety/moderation_pipeline.py`, три ступени (PromptGate по денилисту и возрасту до генерации,
NSFW-классификатор `Falconsai/nsfw_image_detection` после, IdentitySafetyGate с age-estimation и
сверкой по watchlist). Смена чекпойнта на uncensored не отключает ни одну из них.

Лицензионная картина (проверено через HF API):

| Компонент | Лицензия | Коммерческое использование |
|---|---|---|
| `Wan-AI/Wan2.2-TI2V-5B`, `Wan2.2-I2V-A14B` | apache-2.0 | да |
| `rzgar/Wan2.2_LightX2V_4Step_Uncensored` | apache-2.0 | да |
| `JonneyWang/AnyID` | cc-by-nc-sa-4.0 | **нет**, плюс share-alike |
| `black-forest-labs/FLUX.1-dev` | BFL Non-Commercial | **нет** |
| `h94/IP-Adapter-FaceID` | на HF не заявлена | **нет** — некоммерческая по наследству от InsightFace (см. п.4) |
| `nesaorg/PonyRealism-Uncensored` | **не заявлена вообще** | неопределённо |
| `John6666/pony-realism-v23-sdxl`, `illustrious-...-uncensored-v30` | `other` | читать карточку модели |

Два вывода, которые стоит проговорить явно:

1. **Узкое место по лицензиям — не видео, а фото.** В видео-части ограничение ровно одно (AnyID).
   В фото-части ограничен сам FaceID — то есть механизм identity, без которого проект не имеет
   смысла, некоммерческий независимо от выбора чекпойнта.
2. **`nesaorg/PonyRealism-Uncensored` не заявляет лицензию вообще.** Это хуже, чем ограничительная
   лицензия: отсутствие заявления не означает разрешения. Если ветка пойдёт в коммерческое
   использование, безопаснее `John6666/pony-realism-v23-sdxl` (тот же базовый Pony Realism v2.3,
   лицензия хотя бы обозначена) с проверкой карточки модели.

### 8.5. Fast-ветка (A14B + LightX2V), если она понадобится

`deploy/comfyui_uncensored_setup.sh` — ComfyUI-под под FLUX.1-dev + Wan2.2-I2V-A14B + все три
присланные LoRA. Имя файла осталось от первой формулировки задачи; по содержанию это fast-ветка
(4-шаговая LightX2V) плюс Flux. Под создавался и был удалён до скачивания весов, когда направление сменилось на
identity; скрипт оставлен рабочим. Требует A100 80GB (~$1.59/час на Secure) и тома 250 GB под
~106 GB весов.

Две ловушки, заложенные в скрипт намеренно:

- **VAE для A14B — `wan_2.1_vae.safetensors`, не `wan2.2_vae.safetensors`.** Второй относится к
  TI2V-5B; с A14B даст мусор. Файлы лежат рядом в одном репозитории.
- **torch не переустанавливается** — по той же причине, что в п.3 выше.

Доступы проверены прямым запросом с токеном из `.env`: FLUX.1-dev, Flux-uncensored и
LightX2V-репозиторий отдают HTTP 200. FLUX.1-dev числится gated, но этот токен качает его без
ручного принятия лицензии; у другого аккаунта может потребоваться зайти на страницу в браузере.

## 9. Поды из админки

Раздел «Свои карты (RunPod)» (`admin/app.py` + `admin/runpod_pods.py`) — полный цикл без
командной строки: арендовать карту → залить код → поставить окружение → поднять воркер →
пробный кадр → удалить.

Отличие от остальных разделов админки принципиальное: там за вызовом стоит запрос к чужому API,
здесь — арендованная карта, которая **тарифицируется всё время аренды, а не во время генерации**.
Поэтому в списке подов видны наработка и потраченная сумма, а кнопка удаления стоит рядом.

### Что заливается на под

Только код (`worker/`, `safety/`, `runpod_worker/`, `scripts/` — 68 КБ архивом). Веса тянутся на
поде напрямую с HuggingFace: там канал несравнимо быстрее домашнего аплинка. Результаты
забираются обратно по HTTP через прокси RunPod (`https://<podId>-8000.proxy.runpod.net`) — без
отдельного публичного IP.

Свой Docker-образ не собираем намеренно: сборка и заливка занимают больше времени, чем
`pip install` на поде, а обновление кода потребовало бы пересборки вместо `scp`. Берём готовый
`runpod/pytorch:2.4.0-...` и не трогаем в нём torch (п.3).

### Несколько подов одновременно

Поддержано намеренно: SDXL-ветка живёт на 24 GB, Chroma просит 48, видео A14B — 80. Гонять их по
очереди на одной карте значит платить за простой при каждом переключении.

Список строится по **живым подам аккаунта**, а не по реестру админки: под, созданный мимо неё или
оставшийся от прошлой сессии, всё равно тратит деньги и обязан быть виден (помечается как «не из
админки»). Реестр лежит в `runs/runpod_pods.json`, а не в памяти процесса: админку
перезапускают, а карта продолжает тарифицироваться — потерять её id значит платить за под, о
котором забыли.

### Найдено на реальном прогоне

**`runpodctl ssh info` нельзя разбирать по позиции токенов.** Команда собрана как
`ssh -i <путь к ключу> root@<ip> -p <порт>` — `user@host` стоит НЕ вторым токеном. Наивный разбор
давал `host="-i"`, и `scp` падал с `hostname contains invalid characters` уже после того, как
карта арендована. Вдобавок путь к ключу на Windows содержит пробелы, так что разбор строки
ненадёжен в принципе. В JSON есть отдельные поля `ip` и `port` — берутся они, разбор
`ssh_command` оставлен запасным вариантом.

**Имя ключа у runpodctl менялось между версиями** (`RunPod-Key-Go` → `runpodctl-ssh-key`),
поэтому кандидаты перебираются, а не фиксируется одно имя: иначе развёртывание молча падало бы на
`Permission denied` после обновления runpodctl.

**Windows позволяет нескольким процессам слушать один порт.** При отладке админки `pkill` не
убил старые копии, и три экземпляра Flask одновременно держали 5000 — запросы обслуживал самый
старый, то есть правки в коде «не применялись» без единой ошибки в логе. Симптом: исправленный
баг воспроизводится дословно. Проверять `netstat -ano | grep :5000` и убивать по PID, а не по
шаблону командной строки.

**`setsid nohup` при запуске воркера обязателен** — ssh-сессия закрывается сразу после команды, и
без отвязки процесс получил бы SIGHUP и умер вместе с ней.

**Развёртывание идёт в фоновом потоке**, прогресс пишется в лог записи пода: заливка, pip и
первый `/health` занимают минуты, держать на них HTTP-запрос браузера нельзя.

### Пробный кадр

Кнопка «пробный кадр» проверяет связку «карта + чекпойнт + фиксация лица» до запуска полного
пака. Если персонажа на поде ещё нет, он заводится автоматически по карточке из `.env` — то есть
проверяется та же связка, что пойдёт в работу, а не абстрактный промпт. Первый кадр долгий:
тянется чекпойнт и грузится в память.

Выбор режима фиксации лица гасится в интерфейсе для чекпойнтов с `supports_faceid: False`
(Chroma и любые DiT) — ошибка показывается до аренды карты, а не после развёртывания.
